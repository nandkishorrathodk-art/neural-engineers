# Task worker claim protocol

The API exposes a credential-authenticated worker protocol under `/internal/worker`. Prefer `WORKER_API_TOKENS` as a JSON map from stable worker IDs to distinct tokens of at least 32 random characters. The legacy `WORKER_API_TOKEN` is retained as a single `worker-service` identity. Worker identity comes from the validated bearer credential; request bodies cannot choose or impersonate it. Worker credentials must differ from owner and verifier credentials.

1. `POST /internal/worker/tasks/claim` with `{"worker_id":"worker-instance-id"}` leases one assigned, dependency-ready task. The API requires the assigned employee to be reserved and their persisted workstation to be running, then refreshes the workstation status through the restricted Docker broker.
2. The response includes a monotonically increasing `fencing_token`, attempt number, task acceptance criteria, employee ID, and workstation container ID.
3. `POST /internal/worker/tasks/{task_id}/start` must present the same worker ID and fencing token. It rechecks the live workstation and only then records `RUNNING`.
4. Heartbeats extend a live lease. A new claim can take over only after lease expiry or fencing-token revocation; stale workers cannot renew or submit.
5. `POST /submit` stores a nonempty execution receipt on the attempt and returns `submitted_for_verification`. It deliberately leaves the task `RUNNING`; only an independent verifier can complete it. `/fail` records failure and releases the employee.

The separately credentialed verifier protocol uses `VERIFIER_API_TOKEN` (also at least 32 random characters); owner, worker, and verifier tokens must all be different. `GET /internal/verifier/queue` returns current submitted attempts and their acceptance criteria. `POST /internal/verifier/tasks/{task_id}/attempts/{attempt_id}/review` stores a verdict, notes, evidence references, and checks. A passing decision atomically records the receipt, `TaskResult`, completion state, and fencing-token change. A rejected attempt remains available for a later worker retry. Per-worker identity is bound to distinct worker bearer tokens when `WORKER_API_TOKENS` is configured; the legacy single worker token maps to one `worker-service` identity. The verifier token still identifies one service-wide verifier identity, and neither individual identity nor verifier execution is backed by signed attestation yet.

Resource leases are persisted separately through `/internal/resources/leases/claim`, `/{lease_id}/heartbeat`, and `/{lease_id}/release`. Claims are unique for both the resource key and employee while active, expire after a bounded TTL, and issue a monotonically increasing fencing token per resource. These endpoints provide durable lease primitives; `DesktopResourceScheduler` still needs integration with this repository before its legacy in-memory slot manager can use them.

Workstation provision, VNC password rotation, and termination require an owner-created, owner-approved approval ID scoped to the employee and (where applicable) the exact Docker container ID. The approval is consumed atomically immediately before the operation, so it cannot be replayed; an operation failure requires a new approval. Request creation is `POST /security/approvals`, decision is `POST /security/approvals/{id}/decide`, and the operation takes `approval_id` as a query parameter. Approval ID and owner actor are retained in the audit event.

The lease and attempt state share a database transaction with task fencing updates. Task assignment, external GUI actions, and outbox insertion are still not one atomic transaction. Redis message delivery does not execute tasks.

There is not yet a task-worker or verifier process in Compose, nor a production executor connected to the employee desktop. Development mode can use a synthetic desktop for simulations, but production GUI capture rejects synthetic/mock frames and returns unavailable because no live screenshot-based workstation adapter is configured. Until a real desktop adapter and independently operated verifier are deployed, these endpoints are only protocol surfaces and the system must not claim autonomous work has run or completed. A stale/unknown workstation is not leased.
