- Foundational worker/recovery commits `455f752`, `395f53d`, roadmap-doc commit `1e6f897`, and the isolated verifier-consumer slice are included in the current release sequence. The verifier slice has focused evidence but no Docker runtime receipt.
- The opt-in terminal worker lifecycle and verifier rejection retry/backoff/fencing paths have focused tests. Scoped Ruff passed for the new verifier path; Docker profile parsing passed. No live task used the new delta path.
- Resource scheduling now accepts `ResourceLeaseRepository` for durable per-host slot leases, carries fencing tokens in allocation receipts, and heartbeats active claims during scheduler requests. Confirmed shutdown releases claims; provisioning exceptions retain their durable fenced slot until broker-backed cleanup verifies desktop absence. Expired leases remain quarantined while termination is uncertain. Container CPU/RAM limits follow the selected profile. Earlier DB-backed scheduler suites cover competing schedulers and fencing; the latest provisioning/reaper regression passes **8 tests**. `ANCOS_RESOURCE_POOL_ID` scopes shared slots to one host pool. Live service wiring and cleanup after owner-process loss remain unverified.
- Approved workstation endpoints now use DB-backed durable leases: claim precedes provisioning, reads/GUI capture/VNC rotation renew them, and approved termination releases them only after container termination. The API lifespan starts a pool-scoped broker reaper; expiry releases capacity only after broker inspection confirms the managed desktop is absent. Broker uncertainty retains quarantine. Focused mocked API/DB/reaper coverage plus three current-source live lifecycle cycles pass; one cycle recovered after an isolated API restart, and a separate planned broker stop/restart returned HTTP 503 while retaining the lease, then recovered screen capture. Multi-session stress, abrupt crash recovery, broker crash recovery, and live task checkpoint resume remain unverified.
- Live reuse exposed two persistent-state edge cases: a deterministic Docker ID could not be inserted again after a prior terminated session, and a session lookup could choose a released lease when two resource pools had records for the same Docker ID. `ContainerRepository.upsert_current` now updates the existing lifecycle row, and session lookup prefers active/expired records before released history. A retry on the same employee/volume completed provision, capture, approved termination, lease release, and audit verification. Regression tests cover both cases.
- A verifier rejection is persisted, consumes configured retry budget, increments the task fence, backs off before a retry, and sets terminal `FAILED` on exhaustion. This fixes a stuck-task transition; it does not by itself provide a live runtime receipt.
- A separate verifier consumer replays only the submitted attempt's declared `pytest`, Python `unittest`, or `npm test` commands through a verifier-authenticated, attempt-fenced Core API endpoint. The broker runs them in a disposable network-disabled container with a read-only employee-workspace volume and a 300-second timeout, then removes the sandbox. Current source persists a bounded task-start SHA-256 path/size baseline and records a verification-time snapshot plus path/hash delta; this delta has focused unit coverage only, not route-level or live task evidence, and it does not prove artifact correctness. Criteria remain restricted to an exact test-only allowlist.
- A single controlled current-source worker/verifier protocol cycle completed a manually seeded task using a fixed local planner stub, a live broker desktop, separate worker/verifier credentials, and isolated replay. The desktop image lacked pytest; `python3 -m unittest -v` succeeded. Task completed with an independent verified attempt, employee returned IDLE, and approved termination released the lease. It does not establish Boss objective execution, provider planning, long-running profiles, retry/heartbeat/cancel/shutdown behavior, or phase acceptance.
- The claim path now schedules one unassigned, pending DAG task whose prerequisites are completed with persisted passing verifier receipts. It only considers idle employees with an already-running desktop, uses a conditional task assignment update, and then applies the existing worker lease/fencing checks. It cannot provision workstations and preserves the separate approval gate. Tests prove a verified prerequisite unlocks its dependent task, while a legacy completed row without verifier proof does not.
- Retryable worker failures can transfer assignment to an idle employee with a running desktop and no active attempt. The previous employee is released only when no other active attempt remains; failure stays bounded by the existing retry/backoff and fencing rules. The worker API persists a BossAI recovery audit event with previous and new assignee IDs. Repository/API regressions cover the transfer and audit event, but not live failure injection or live desktop transfer.
- Safe stale-task recovery is now explicit and scoped: the owner requests a recovery approval; an independent approver decides it; the owner consumes it only after the API has confirmed there are no task attempts, no active or quarantined employee/workstation lease, and the restricted broker returns 404 for the deterministic desktop ID. The repository rechecks task status, assignment, fencing token, no-attempt state, lease absence, and approval scope under row locks; it atomically consumes the approval, marks a stale container record FAILED, requeues/unassigns the task, increments the fencing token, conditionally idles the employee, and appends the audit hash-chain entry. A focused production-auth API/DB regression passed, including rejection of owner self-approval. This is source-only and does not change the live user database; tasks with prior attempts remain outside this recovery path and need separate diagnosis.
- **NEURO-12 resilience hardening:** Cryptographic audit log verification (`AuditLogChainVerifier.verify_records`) and `AuditRepository.create_entry` deterministically bind and re-hash both `payload` and `details` when present, validating against `request_hash` to detect unauthorized modifications to either field; verification rejects missing signatures and forged/wiped `request_hash` values even on terminal chain blocks. Global emergency kill switch guards are enforced across all remote worker routes (`claim`, `start`, `heartbeat`, `exec`, `submit`, `fail`) and verifier routes (`queue`, `exec`, `manifest`, `review`), returning HTTP 503 (`EmergencyStopTriggered`) when halted, while `TerminalWorker` and `VerificationWorker` client loops safely abort/back off without corrupting task states. `DisasterRecoveryManager.restore_backup` enforces dual pre-extraction disk exhaustion guards checking filesystem free space against archive staging size and inspecting uncompressed member headers against free space to prevent decompression exhaustion. Focused resilience tests in `test_neuro_phase12_resilience.py` and tamper tests in `test_phase6_observability.py` pass (38 passed).
